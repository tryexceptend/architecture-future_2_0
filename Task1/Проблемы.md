# Проблемные места

1. Защищенность данных.
   1. В текущей архитектуре конфедициальные данные пользоватетей не защищены в соответствии с 153-ФЗ. Нужно перенести данные в защищенное хранилище
   2. Все данные хранятся в одном месте. SQL хранилище требует значительных усилий по масштабированию. 

2. Сложность интеграции сторонних систем.
   1. Необходимо инетгрировать в систему много сторонних сервисов. Для ускорения и упрощения процесса нужно использовать единую систему или механизм интеграции.
   2. Сторонние сервисы должны придерживаться единого формата данных.

3. Техдолг. Старые системы тяжело поддерживать.
   1. Нужны специалисты с уникальным опытом. Это стоит денег и времени на обучение новых
   2. У системы Power Builder есть ограничения на инфраструктуру. Нужны определенные операционные системы и устаревшее железо. Это ограничивает эффективное масштабирование и доработку системы. 
   3. Отсутствует тестирование, что плохо сказывается на скорости выпуска обновлений.

4. Систему клиник тяжело масштабировать. 
   1. Бизнес логика представляет собой скрипты в SQL-сервере. Такое решение очень тяжело масштабировать и поддерживать.
   2. Объем данных постоянно увеличивается. Это ведет к замедлению работы скриптов и обработки бизнес-логики.  
5. Разнообразие бизнес-продуктов.
   1. Много разных бизнес процессов тяжело контролировать вместе. Это создает путаницу для сотрудников и сложность поиска информации в большом объеме разнообразных данных в DWH.\
6. Обучение персонала
   1. Переход на схему с "витриной данных" потребует обучению персонала новому функционалу. Для этого в процессе разработки надо уделить внимание документации. Создать портал для обучения, проводить тренинги персонала.

# Приоритезация

1. **M**ust (обязательно)
   
   - **Защищенность данных.** Нужно повысить защищенность данных клиентов и компании. Необходимо создание департамента информационной безопасности. Он будет ответственен за реализацию и контроль мер защиты данных, разработку тредований к системе и их соблюдение. 
   - **Старые системы тяжело поддерживать.** Система построена на базе SQL-сервера с бизнес логикой в скриптах. Нужно реализовать перестройку системы на микросервисную архитектуру. Это позволит масштабировать систему, оптимизировать работу.

2. **S**hould (нужно)
   
   - **Сложность интеграции сторонних систем.** Для интеграции систем используется шина на базе Apache Camel. Для систематизации подхода надо разработать стандарты интеграции. Часть систем можно интегрировать сразу в "витрину данных" DataHub, что снизит нагрузку на шину. Ее можно использовать для межсистемного взаимодествия.
   - **Разнообразие бизнес-продуктов.** Большое количество разных бизнес-моделей может привести к хаосу. Надо выделить команду "Платформа", которая разработает стандарты для интеграции новых систем. Их желательно оставить замкнутыми системами, которые будут предоставлять данные другим доменам через "Витрину данных"

3. **C**ould (желательно)
   
   - **Обучение персонала .** Внедрение нового функционала в начале скажется на скорости работы среди персонала. Желательно проводить тренинги среди сотрудников по новым продуктам. Создать информационный портал с материалами. 

4. **W**on’t Have this time (можно перенести)
   
   - **Избавление от DWH.** Процесс трансформации системы будет долгий. Поэтому перенос данных с DWH можно отложить. Накопленные в нам данные можно продолжать использовать, получая их через "витрину данных".
